## 总体图设计

总体图采用纵向 A4 比例，形成自上而下的主研究链和左右支撑关系。

### 顶部：总体目标

标题为“面向持续动态对抗的主机安全技术路线”。目标框用浅蓝色，正文为“在可控资源成本下形成可调整、可关联、可复核、可验收的 Linux 主机安全能力”。

### 左列：关键问题

左列使用浅蓝色箭头或矩形，依次回答四个问题：

1. 如何持续看见关键主机行为，同时控制资源消耗？
2. 如何从海量行为记录中提炼高价值安全线索？
3. 如何在明确边界内关联分散信息并组织调查依据？
4. 如何根据风险和运行状态安全地调整防御策略？

### 中列：研究内容

中列是全图主轴，使用浅红色标题框和白色子任务框，自上而下递进：

1. 可信、低成本的主机行为观测：行为规范化、作用域控制、有界保存、缺失显式报告。
2. 端侧实时筛选与行为线索提炼：规则与上下文、局部关联、来源引用、断网自治。
3. 中心侧限定关联与调查依据组织：历史窗口、实体关系、稳定收敛、调查下钻。
4. 统一策略控制与闭环验证：采集、检测、传输、响应统一调控，确认审计和分层测试。

每项研究内容下设置 3—4 个等宽子任务框。相邻任务之间使用粗实线向下箭头，表示输入和能力递进。

### 右列：研究方法

右列使用浅绿色方法框，以虚线连接对应研究内容：

- 内核运行时观测、统一行为语义、有界存储与故障计数；
- 规则匹配、复杂事件处理、上下文关联与稳定来源标识；
- 时间窗口、实体关系图、邻域与路径查询、确定性重算；
- 版本化策略、原子应用、权限审批、故障注入和对照实验。

### 底部：验证和成果

底部先以虚线分区展示三类验证：产品链路验证、恶意与良性场景验证、独立资源与长稳验证。最下方浅黄色成果框统一收敛为：

“形成端侧自主运行、中心侧关联分析、策略统一管控和效果客观验证的平台能力”。

图底增加小型成熟度图例：实线边框表示当前已有工程基础，双色或加粗边框表示建设期重点，虚线边框表示需独立研究验证。图中不得把原始材料真实回取、完整因果路径推理、自然语言解释和真实自动阻断画成当前能力。

## 三张专题图设计

### 动态博弈：统一策略闭环

采用“环境与威胁变化—策略形成—安全校验—端侧应用—状态反馈—下一轮调整”的顺时针闭环。中心放置统一策略，向四周展开“观察什么、识别什么、传输什么、允许做什么”四个可调层面。右下方单列安全约束：作用范围、资源预算、版本、审批、确认和审计。

图中明确当前边界：目前已具备统一策略、校验、下发、确认和审计基础；风险触发的自动加深、自动恢复和真实阻断仍需研究验证。

### 效能平衡：安全信息逐级提炼

采用自左向右的漏斗式主链：

“大量行为记录 → 较少行为线索 → 可复核调查依据 → 综合研判结论”。

主链上方展示安全信息价值逐级提高，下方展示数据规模逐级降低。每层分别标明保留内容、处理位置和资源约束。底部增加反馈箭头，表示材料不足时只能在授权范围和时间窗口内补充观察。

图中明确“行为线索不等同于告警”，并区分当前已有的实体关系子图与仍待实现的真实原始材料回取。

### 端云协同：分工与联合分析

采用左右双域结构：左侧为“受保护主机”，右侧为“安全管理平台”，中间为“可靠、受控的数据与策略通道”。

端侧依次展示行为观测、本地筛选、初步判断、有界保存和断网续运行；中心侧依次展示身份校验、限定历史关联、实体关系分析、集中研判和统一查询。上行链路只传输策略允许的高价值信息，下行链路只传输经过版本化和校验的策略及受控命令。

图底设置“调查核实—授权处置—策略优化”运营闭环，并用三类测试覆盖端侧、传输和平台。平台不可用不得使端侧停止工作，中心侧关联不得跨越组织和业务作用域。

## 视觉规范

- 画布：白色背景；总体图优先使用 1200 × 1800 的纵向页面，专题图使用 1400 × 900 的横向页面。
- 字体：中文使用无衬线字体，标题 24—28 px，分区标题 19—22 px，节点正文 15—18 px；英文产品名和 Linux 保持原样。
- 配色：目标与问题使用浅蓝 `#D9ECF8`，研究内容使用浅红 `#F7D9DC`，研究方法使用浅绿 `#DDF0D2`，验证与成果使用浅黄 `#F8E8B8`，辅助区域使用浅灰 `#F5F6F7`。
- 线条：主流程使用 2 px 深灰实线和实心箭头；支撑关系使用 1.5 px 深灰虚线；分区边界使用蓝灰色点划线。
- 形状：矩形保持小圆角或直角，不使用阴影、渐变、立体效果、图标和装饰性背景。
- 布局：同层节点等宽等高，文字水平和垂直居中；连线采用正交折线，禁止穿过节点和文字。
- 语言：图内只使用面向业务和研究评审的中文。Agent、Event、Signal、Evidence、Incident 等工程名称不得出现在主图正文。

## 文件与一致性约束

`.drawio` 是可编辑几何和文本的源文件，`.svg` 是 Markdown 引用的交付文件。每一组文件必须具有相同的可见文字、节点位置、颜色和连线关系。SVG 应包含可访问的 `title` 和 `desc`，并使用可缩放的 `viewBox`。

正式架构定义仍以 `docs/design-principles.zh-CN.md` 和 `docs/architecture.md` 为准。图表只概括事实，不独立引入新的产品能力、性能承诺或实施范围。

## 验收标准

1. 四组 Draw.io 与 SVG 文件均存在，并能在 XML 解析器中正常读取。
2. 建议书中的四处图表引用均指向存在的 SVG，不再保留重复 Mermaid 图。
3. 总体图可以独立回答“为什么做、研究什么、怎么做、如何验证、形成什么成果”。
4. 三张专题图分别完整表达动态博弈、效能平衡和端云协同，且不与总体图重复堆字。
5. 所有正文节点在 100% 缩放和文档内 90% 宽度下可读，无文字裁切、连线穿字和节点重叠。
6. SVG 转为 1200 px 宽的 PNG 后进行人工视觉检查；总体图和三张专题图均无空白、越界或异常字体。
7. 全仓旧图引用、相对链接和 `git diff --check` 检查通过。
