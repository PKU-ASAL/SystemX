# SysArmor 整体介绍 Word 设计

## 目标与受众

生成一份可编辑的中文 `.docx`，用于政府或科研合作沟通、产业客户介绍和早期投资交流。正文从第一性原理解释 SysArmor，不假设读者熟悉端点安全、EDR、系统溯源或流式数据平台。

文档不是仓库 README、投资 Pitch 或技术架构文档的拼接。它必须先回答“为什么存在这个问题”，再推出“一个有效系统必须满足什么”，最后解释 SysArmor 的选择、证据和当前边界。

## 核心叙事

整篇围绕一个判断展开：终端安全真正稀缺的不是更多日志，而是在可接受成本下保留必要上下文，及时形成判断，并让判断能够被复核。

由此推导五个必要条件：

1. 看见关键行为，同时控制端侧资源成本；
2. 在端点本地及时形成初步判断，网络中断时仍能工作；
3. 在集中平台中把分批到达的局部判断放回同一上下文；
4. 保留结论、贡献 Signal 和实体 Evidence 之间的关系；
5. 用独立测试分别证明产品链路、检测效果和资源成本。

SysArmor 的产品与工程选择必须逐项回应这五个条件。

## 章节结构

### 1. 封面与一句话定义

标题为“SysArmor：面向 Linux 的智能终端安全与关联分析平台”。副标题强调“从主机行为到可验证的安全结论”。封面不写融资金额，不使用未经授权的机构 Logo。

### 2. 为什么终端安全仍然难

从攻击发生在进程、文件、网络和身份行为中讲起，解释采得少会丢上下文、采得多会增加成本、孤立告警需要人工拼接、敏感数据要求私有化。避免先介绍产品组件。

### 3. 从第一性原理推导系统要求

用五个必要条件建立全文逻辑。每个条件采用“问题—系统必须做到什么—如何验收”三句结构，不罗列技术名词。

### 4. SysArmor 的基本选择

解释 Agent 默认独立运行，注册只增加集中上传和控制；本地路径不因平台接入而改变。配 `product-flow.svg`，并用普通语言解释端点与平台的分工。

### 5. 一次安全行为如何形成结论

用一个抽象 staged 场景串联事件、Endpoint Signal、历史窗口、Cloud Signal、Incident 和 Evidence。明确当前实现是规则化 Signal 组合与稳定投影，不宣称已实现完整路径推理或自然语言根因分析。

### 6. 总体技术路线

配 `technical-roadmap-b-narrative.svg`。正文只解释可信行为、局部 Signal、跨批关联、结构化 Incident 与三类验证，不逐个展开 Gateway、Kafka、Worker 和数据库名。

### 7. 关联方法

配 `correlation-method-b-lecture.svg`。解释当前 batch 与同一分析作用域的 15 分钟历史窗口如何进入同一 Signal View；Endpoint Signal 文档身份按 tenant、Agent 和 Signal ID 隔离，但历史关联边界按 tenant 与分析标签限定。

### 8. 当前产品状态与边界

用“已经具备”“产品化中”“规划/验证中”三栏表格区分现状。已经具备包括 standalone Agent、本地检测与有界存储、注册和证书、可靠上传、跨 batch 历史关联、稳定投影及基础查询；完整 Incident UI、完整事件回溯、时间推理、路径排序和增强解释不得写成现状。

### 9. 如何证明系统真实有效

分别介绍产品测试、攻击/良性场景检测测试和独立虚拟机性能测试。说明每类测试的输入、输出和能证明的边界，避免用“测试通过”替代具体含义。

### 10. 从研究积累到工程能力

以“可信采集、在线关联、证据表达、可部署工程”四类能力组织 NoDrop、NodLink、DPUaudit、KnowHow 等研究基础。论文和研究系统只说明能力来源，不直接等同于当前产品指标。

### 11. 试点观察与适用场景

使用已有谨慎口径：相关技术或历代平台累计覆盖超过 1000 台终端，记录 40 余次关键安全隐患，内部记录平均响应耗时低于 5 分钟。明确这些是跨环境、内部未审计统计，不代表当前版本在所有机构的生产部署。

### 12. 商业化与开放路径

解释私有化部署、平台许可、实施服务和年度维护。仓库当前没有许可证，因此开放核心只能写成完成确权和许可证设计后的计划。

### 13. 下一阶段要证明什么

用产品标准化、付费 PoC、行业复制、规模化交付和知识产权确权五项可验证目标收束，不写融资金额。

### 14. 结语

回到核心判断：项目价值不在于制造更多告警，而在于将长期系统安全研究组织成可运行、可测量、可交付的产品。

## 版式

- A4 纵向，正文约 12–15 页，附录约 2–3 页。
- 正文中文使用无衬线字体，正文 10.5–11 磅，标题按三级层次递减。
- 每页保留页眉“SysArmor 项目整体介绍”和页码。
- 采用白底、深灰正文、蓝绿为主强调色，红色只标识边界或风险。
- 图表居中，宽度不超过正文版心；每张图下方提供一句解释和“当前/规划”图例。
- 不使用大段背景色、装饰性渐变、营销口号页或密集卡片。

## 文件与生成方式

- 新增正文源文件 `docs/business/sysarmor-overview.zh-CN.md`，便于版本审查和后续修改。
- 生成交付文件 `docs/business/sysarmor-overview.zh-CN.docx`。
- 使用 Pandoc 生成基础 Word，并通过参考 DOCX 或 Lua filter 设置标题、页眉页脚、图宽和分页。
- 使用 LibreOffice headless 将 DOCX 转为 PDF 做页数、分页和渲染验证；PDF 只作为临时检查产物，不提交仓库。

## 验收标准

1. DOCX 可由 LibreOffice 无错误打开并转换为 PDF。
2. 正文与附录总页数目标为 14–18 页；若因字体环境偏差超出，优先调整段落密度，不删事实边界。
3. 五张正文图和两张附录图可见、比例正确、无裁切；正文至少包含 product flow、两张 B 版技术图，并可按篇幅选用 defensibility 与 business flywheel。
4. 文档不存在 TODO、TBD、硬编码密钥、融资金额或无依据的成熟度陈述。
5. 当前能力、产品化中能力和规划能力在文字与图中保持一致。
6. 中文正文以自然段组织，避免连续术语堆叠；每个必要技术词第一次出现时给出普通语言解释。
7. Markdown 源文件相对图片路径有效，DOCX 解包后包含所有实际引用媒体。
