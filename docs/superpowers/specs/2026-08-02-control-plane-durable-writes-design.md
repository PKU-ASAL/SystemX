# Control Plane Durable Writes Design

## 结论

EDR 控制面写操作必须在持久化失败时显式失败，且不能把未持久化状态作为成功状态暴露。此次改造覆盖响应命令、响应确认、控制命令、控制命令确认、策略发布和策略分配六条高敏路径。

## 当前问题

- `CreateResponse`、`AckResponse`、`PublishPolicy` 和 `AssignPolicy` 忽略后端写入错误。
- `CreateControlCommand` 和 `AckControlCommand` 只能依赖调用方执行全量 `SaveState`，方法本身没有可靠的持久化结果。
- Manager 和 Gateway 无法区分对象不存在与基础设施写入失败。
- 策略发布包含审计记录，策略分配可能同时产生审计记录和下行控制命令；逐项提交会产生部分成功。

## 设计

### 错误语义

- 创建操作返回 `(T, error)`。
- 查找后更新操作返回 `(T, bool, error)`；`bool=false, error=nil` 表示业务对象不存在或前置条件不满足，`error!=nil` 表示持久化失败。
- Manager 将业务不存在映射为 `400/404`，将持久化错误映射为 `500`。
- Gateway 将业务不存在映射为 `NotFound`，将持久化错误映射为 `Internal`，失败时不得返回 accepted。

### 持久化边界

- 为 `Backend` 增加单条控制命令写接口，使控制命令和响应、策略、分配具有同样的持久化能力。
- 单实体操作在后端写入成功后才发布新的内存状态；失败时保留原状态。
- 内存模式不执行持久化，可继续用于单元测试。
- 文件模式继续通过原子文件保存完成持久化；调用方不得把保存失败视为成功。

### 业务原子性

- 策略发布与对应审计记录属于同一个业务提交。
- 策略分配、对应审计记录及可选下行控制命令属于同一个业务提交。
- 复合提交复用现有 `SaveState` PostgreSQL 事务，不引入通用事务框架。
- 任一步骤失败时恢复本次操作前的内存状态。

### 兼容策略

六个高敏方法直接迁移为显式错误签名，并更新仓库内全部调用点。不得保留会静默吞错的同名兼容入口；测试辅助调用也必须显式处理错误。

## 测试与验收

- 每条路径都有失败后端测试，验证返回错误且内存状态不变。
- Manager API 持久化失败返回 `500`。
- Gateway ACK 持久化失败返回 `Internal`，不返回 accepted。
- 策略复合操作失败后，策略、分配、审计和控制命令均不出现部分更新。
- `go test ./...`、`go vet ./...` 和相关包 `go test -race` 通过。

## 非目标

- 不重构 Store 的所有写操作。
- 不引入通用 Unit of Work、事件溯源或消息队列。
- 不改变控制命令协议和策略业务规则。
